# etl-statsmig

Upgrades ET:Legacy match statistics JSON files from the **old format (stats_version 1.2.4)** to the **new format (stats_version 2.x)**. Designed to process thousands of files totalling hundreds of gigabytes in parallel, reliably and without touching source files.

---

## Background

Match statistics are generated by a Lua module running inside the ET:Legacy game server. The format changed significantly between versions:

| Feature | Old (≤ 1.2.4) | New (≥ 2.0.0) |
|---|---|---|
| `gamelog` event array | ✗ | ✓ |
| `metadata` section | ✗ | ✓ |
| Version fields in `round_info` | ✗ | ✓ |
| `messages` in `round_info` | ✓ (removed in new) | ✗ |
| `obituaries` in `round_info` | ✓ (removed in new) | ✗ |
| `damageStats` in `round_info` | ✓ (removed in new) | ✗ |
| `class_switches` in `player_stats` | ✓ (removed in new) | ✗ (moved to gamelog exclusively) |
| Shoves format in `player_stats` | `{leveltime: guid_string}` | `{leveltime: {objective, timestamp_unix}}` |
| `obj_*` format in `player_stats` | `{leveltime: obj_name_string}` | `{leveltime: {objective, timestamp_unix}}` |

Old files do **not** have a `stats_version` field — this is how the tool detects them. New files have `stats_version` in `round_info`.

## Commands

### `upgrade` — Upgrade old files to new format

```
etl-statsmig upgrade --in <dir> --out <dir> [--workers N]
```

**Flags:**

| Flag | Default | Description |
|---|---|---|
| `--in` | (required) | Source directory. Walked recursively for `*.json` files. |
| `--out` | (required) | Destination directory. Input directory structure is mirrored exactly. |
| `--workers` | `runtime.NumCPU()` | Number of parallel goroutines. Increase for I/O-bound storage. |

**Examples:**

```bash
# Basic upgrade
etl-statsmig upgrade --in /data/stats/old --out /data/stats/upgraded

# Explicitly set worker count for a fast NVMe array
etl-statsmig upgrade --in /data/stats/old --out /data/stats/upgraded --workers 32
```

**Behaviour:**

- Source files are **never modified**.
- Output directory and all subdirectories are created automatically.
- Files already containing a `gamelog` key (i.e. already upgraded) are **skipped** without error.
- A progress line is printed every 1,000 files.
- Exits with code `1` if any file failed.

---

### `rescore` — Re-inject `metadata.scores` in already-upgraded files

```
etl-statsmig rescore --in <dir> [--workers N]
```

Replays the ET stopwatch scoring algorithm over every upgraded file in `--in` and writes the computed `metadata.scores` payload into each round in-place.

> **Note:** `upgrade` already runs scoring as part of its pipeline. `rescore` exists as a separate utility for cases where you need to re-score previously upgraded files — for example, after a scoring algorithm fix, or to update files that were upgraded before scoring was integrated.

**Flags:**

| Flag | Default | Description |
|---|---|---|
| `--in` | (required) | Directory with already-upgraded JSON files. Modified in-place. |
| `--workers` | `runtime.NumCPU()` | Number of parallel goroutines. |

**Behaviour:**

- Reads `match.rounds[]` in order, replays scoring round-by-round.
- Injects one `RoundScores` object per round into `round_data.metadata.scores`.
- If the computed final score differs from any stored `match.alpha_score` / `match.beta_score` / `match.winner`, a `WARN` line is printed.
- Files without a `rounds` key are skipped silently.
- Source file mtime is intentionally **not** updated on rescore.
- Exits with code `1` if any file errored.

**Example:**

```bash
etl-statsmig rescore --in /data/stats/upgraded
```

---

### `scorecheck` — Dry-run scoring algorithm against reference files

```
etl-statsmig scorecheck --ref <dir>
```

Reads already-scored new-format files from `--ref`, re-computes scores from scratch using the same algorithm as `rescore`, and reports pass/fail per round.

**Flags:**

| Flag | Default | Description |
|---|---|---|
| `--ref` | (required) | Directory with reference new-format JSON files (already containing `metadata.scores`). |

**Behaviour:**

- For each file, reads `round_info` fields to reconstruct `scoreRoundInput` values and reads existing `metadata.scores` as the expected output.
- Computes scores independently and compares field-by-field: `alpha`, `beta`, `completed_maps`, `match_finished`, `match_winner`, `round.{map_num,round_num,winner,winner_et,alpha_side,fullhold}`.
- Rounds without stored scores (old-format files in the ref dir) are skipped.
- Prints `[PASS]` / `[FAIL]` per file and a summary table.
- Exits with code `1` if any round failed.

**Example:**

```bash
etl-statsmig scorecheck --ref /data/stats/new_reference_samples
```

---

### `validate` — Validate upgraded files

```
etl-statsmig validate --in <dir> --out <dir> [--ref <dir>] [--workers N] [--verbose]
```

**Flags:**

| Flag | Default | Description |
|---|---|---|
| `--in` | (required) | Directory with original (old-format) source files. Used for count and data-integrity checks. |
| `--out` | (required) | Directory with upgraded output files to validate. |
| `--ref` | (optional) | Directory with reference new-format files. Used for structural schema comparison only. |
| `--workers` | `runtime.NumCPU()` | Number of parallel goroutines. |
| `--verbose` | `false` | Print `[PASS]` and `[WARN]` lines. Without this only failures are printed. |

Exits with code `1` if any file has errors.

A log file is always written to the current working directory: `validation_YYYY_MM_DD-HH_MM_SS.log`. The log mirrors stdout exactly — `[FAIL]` lines always appear, `[PASS]` and `[WARN]` lines only when `--verbose` is set.

**Examples:**

```bash
# Validate upgraded files against originals
etl-statsmig validate --in /data/stats/old --out /data/stats/upgraded

# Full validation with verbose stdout and reference schema comparison
etl-statsmig validate --in /data/stats/old --out /data/stats/upgraded --ref /data/stats/new --verbose
```

## What the Upgrade Does

For every `*.json` file found recursively in `--in`, the upgrader:

### 1. Detects already-upgraded files

If `round_info.stats_version` is already present, the file is **skipped**. This makes the tool safe to re-run.

### 2. Adds version fields to `round_info`

All three fields are injected with the known values for the 1.2.4 generation:

```json
"stats_version": "1.2.4",
"et_version":    "ET 2.60b linux-x86_64 May  8 2006",
"mod_version":   "v2.83.1-34-ga127043"
```

### 3. Removes old collection fields from `round_info`

The `messages`, `obituaries`, and `damageStats` arrays are removed from `round_info`. Their data is migrated into the `gamelog` array (see §5).

### 4. Builds the `metadata` section

A new top-level `metadata` key is added to each `round_data`:

```json
{
  "servername":   "...",
  "config":       "...",
  "matchID":      "...",
  "server_ip":    "...",
  "server_port":  "...",
  "stats_version": "1.2.4",
  "et_version":   "ET 2.60b linux-x86_64 May  8 2006",
  "mod_version":  "v2.83.1-34-ga127043",
  "features":     null,
  "scores":       { ... }
}
```

`features` is `null` because old files pre-date the gather automation system that populates it. `scores` is computed and injected automatically by the upgrade pipeline (see §5 and the scoring algorithm).

### 5. Builds the `gamelog` array

The gamelog is a chronological event timeline. Events are sourced from all available old data:

| Source | Gamelog label | Notes |
|---|---|---|
| Synthetic | `round_start` | Always first. `leveltime` = `round_info.round_start`. |
| `round_info.messages[]` | `message` | `guid`→`player`, `timestamp`→`leveltime` |
| `round_info.obituaries[]` | `kill` / `suicide` / `teamkill` | Disambiguated by comparing attacker/victim teams from `player_stats`. Self-kill or missing attacker → `suicide`. Same team → `teamkill`. |
| `round_info.damageStats[]` | `damage` | `attacker`→`killer`, `target`→`victim`, `hitRegion`→`hit_region`, `damageFlags`→`damage_flags`, `meansOfDeath`→`weapon` |
| `player_stats[*].shoves_given` | `shove` | Only `shoves_given` iterated to avoid duplicate events with `shoves_received`. |
| `player_stats[*].class_switches[]` | `class_change` | `toClass`→`class`, `timestamp`→`leveltime` |
| Synthetic | `round_end` | Always last. `leveltime` = `round_info.round_end`. |

The gamelog has two distinct families of objective event, each with its own label and payload:

**Standard objective events** — each is a completely separate gamelog event type with its own label, carrying an `objective` field with the config-defined name of the objective involved:

| Source | Gamelog label | Notes |
|---|---|---|
| `player_stats[*].obj_planted` | `obj_planted` | Player planted a charge on an objective |
| `player_stats[*].obj_defused` | `obj_defused` | Player defused a planted charge |
| `player_stats[*].obj_destroyed` | `obj_destroyed` | Player destroyed an objective |
| `player_stats[*].obj_repaired` | `obj_repaired` | Player repaired a destroyed objective |
| `player_stats[*].obj_taken` | `obj_taken` | Player picked up a movable objective (flag/document) |
| `player_stats[*].obj_secured` | `obj_secured` | Player scored a movable objective at the capture point |
| `player_stats[*].obj_returned` | `obj_returned` | Player returned their team's stolen objective to base |
| `player_stats[*].obj_carrierkilled` | `obj_carrierkilled` | Player killed an objective carrier. Old value format is `{victim, weapon, objective}` — only the `objective` name is emitted into the gamelog event; `victim` and `weapon` remain in `player_stats` only. |

**Flag capture event** — a completely separate event type from all objective events above, with its own label. Carries a `flag` field (e.g. `"allies_flag"`, `"axis_flag"`) identifying which flag was captured:

| Source | Gamelog label |
|---|---|
| `player_stats[*].obj_flagcaptured` | `obj_flag_captured` |

**Player_stats-only tracking (no gamelog events):**

`obj_misc` and `obj_escort` are tracked in `player_stats` but do **not** generate gamelog events — they are not part of the `ObjectiveLabel` event type in the new format. Their player_stats values are still format-upgraded (`timestamp_unix` added).

**Ordering:** Inner events (everything between `round_start` and `round_end`) are sorted ascending by `leveltime`. The two bookend events are always forced to first and last position regardless of their leveltime values, because player-side events (e.g. class changes at round teardown) can legitimately carry leveltimes outside the nominal round window.

**Timestamp inference (`unixtime`):**

Every gamelog event carries a `unixtime` in milliseconds when `round_start_unix` is available in `round_info`:

```
event_unixtime_ms = (round_start_unix × 1000) + (event_leveltime − round_start_leveltime)
```

If `round_start_unix` is absent (some very early files), `unixtime` is omitted from all events.

**`match_id` field in gamelog events:**

Uses `round_info.original_match_id` (the server-side match number). In old files where `original_match_id` equals the UUID filename, the UUID is used.

### 6. Upgrades `player_stats`

#### `class_switches` removal

`class_switches` is **deleted** from `player_stats`. Its data is migrated exclusively into the `gamelog` array as `class_change` events (see §5). No `class_switches` key appears in any upgraded `player_stats` entry.

#### `shoves_given` / `shoves_received` format upgrade

Old format — value is a plain GUID string:
```json
{"560221": "C7591A4285B07480F002220A52AC7189"}
```
New format — value is an object with `timestamp_unix` in seconds:
```json
{"560221": {"objective": "C7591A4285B07480F002220A52AC7189", "timestamp_unix": 1770648727}}
```

#### `obj_*` format upgrade (all except `obj_carrierkilled`)

Old format — value is a plain objective name string:
```json
{"671744": "gold_crate"}
```
New format:
```json
{"671744": {"objective": "gold_crate", "timestamp_unix": 1770648797}}
```

`obj_flagcaptured` retains its key name in `player_stats` (new format also uses `obj_flagcaptured`, not `obj_flag_captured`).

`obj_carrierkilled` is passed through unchanged as its old value structure is complex and varies.

#### `timestamp_unix` calculation for player_stats entries

```
timestamp_unix_seconds = round_start_unix + (leveltime − round_start) / 1000
```

Returns `0` and omits upgrading when `round_start_unix` is absent.

### 7. Restores file modification time

After writing the output file, the tool calls `os.Chtimes` to set both `atime` and `mtime`:

- **Primary:** `match.end_time` (unix seconds)
- **Fallback:** `match.start_time` if `end_time` is zero or absent

This preserves the original chronological position of files in directory listings.

## What Cannot Be Reconstructed

The following data exists in new-format files but was never recorded by the old Lua module. These fields and event types will be absent from upgraded files:

| Missing | Reason |
|---|---|
| `spawn` gamelog events | Old module had no spawn callback logging |
| `revive` gamelog events | Old module had no revive callback logging |
| `pickup` gamelog events | Old module had no item pickup logging |
| `weapon_fire` gamelog events | Old module had no per-shot logging |
| `killer_pos`, `victim_pos` on kill/damage events | Position not recorded in old obituary/damage data |
| `killer_class`, `victim_class` on kill/damage events | Class not recorded in old obituary/damage data |
| `killer_health`, `victim_health` on kill/damage events | Health not recorded in old data |
| `killer_stance`, `victim_stance` on all events | Stance snapshots not recorded in old data |
| `axis_alive`, `allies_alive` on kill events | Alive counts not recorded in old data |
| `vsay_text` on message events | vsay text expansion not stored in old messages |
| `flag` on `obj_flag_captured` (gamelog) when not in player_stats | Cross-referenced from player_stats only |
| `metadata.features` | Gather automation system post-dates old files |
| `metadata.scores` | Score tracking system post-dates old files |
| `player_stats[*].player_speed` | Speed tracking post-dates old files (not present in 1.2.4) |

## Validation Checks

`validate` performs the following checks on each `(old, out)` file pair:

### Structural checks
- Output file is valid JSON with a `match` key
- Round count matches between old and out
- Each `round_data` has `round_info`, `player_stats`, `gamelog`, `metadata` keys

### `round_info` checks
- `stats_version` = `"1.2.4"`
- `et_version` = correct value
- `mod_version` = correct value
- `messages`, `obituaries`, `damageStats` are **absent**
- Core fields (`round`, `mapname`, `matchID`, `winnerteam`, `round_start`, `round_end`) are **unchanged** from old file

### `metadata` checks
- All required keys present: `servername`, `config`, `matchID`, `server_ip`, `stats_version`, `et_version`, `mod_version`, `features`, `scores`
- Version fields match expected constants

### `gamelog` checks
- Array is non-empty
- First event label = `round_start`
- Last event label = `round_end`
- All inner events are sorted ascending by `leveltime`
- All events have required fields: `group`, `label`, `match_id`, `round_id`, `leveltime`
- `obj_flag_captured` events have `flag` field (not `objective`)
- **Count checks against old data:**
  - `message` event count = `len(old.round_info.messages)`
  - `kill + suicide + teamkill` event count = `len(old.round_info.obituaries)`
  - `damage` event count = `len(old.round_info.damageStats)`
- Spot-check of `unixtime` consistency: `|unixtime − expected| ≤ 5000 ms` for first 20 events (when `round_start_unix` available)

### `player_stats` checks
- All player GUIDs from old file present in output
- `class_switches`: key must be **absent** from all `player_stats` entries (data lives exclusively in gamelog as `class_change` events)
- `shoves_given` / `shoves_received`: values are objects with `objective` and `timestamp_unix` (not plain strings)
- All `obj_*` values are objects with `objective` and `timestamp_unix` (not plain strings)
- `timestamp_unix` values in shoves/obj entries are within ±60 seconds of the inferred expected value (when `round_start_unix` available)

### File mtime check
- Output file mtime matches `match.end_time` (or `match.start_time`) within ±2 seconds

### Structural reference comparison (`--ref`)
When `--ref` is provided, the validator extracts all JSON key paths from the reference files (normalising dynamic keys: GUIDs → `<guid>`, Discord snowflake IDs → `<snowflake>`, leveltime/timestamp keys → `<timestamp>`), then checks each output file for missing schema paths. Paths that cannot be reconstructed from old data are automatically suppressed as expected-absent.

## Performance

The tool uses a goroutine worker pool. Each goroutine independently reads, transforms, and writes one file at a time — no shared mutable state.

**Benchmark (development machine, local NVMe):**

| Files | Avg size | Time | Rate |
|---|---|---|---|
| 600 | ~270 KB | ~3 s | ~200 files/s |

For hundreds of GB spread across thousands of files, runtime is dominated by storage throughput. Guidelines:

- **Local NVMe:** Use `--workers $(nproc)` (or up to 2×)
- **Network storage (NFS/SMB):** Increase `--workers` significantly (64–256) to saturate bandwidth despite per-file latency
- **Spinning disk:** Keep workers low (4–8) to avoid seek thrashing

**Memory:** Each goroutine holds one file in memory at a time. Peak usage ≈ `workers × max_file_size`.

## Production Workflow

```bash
# 1. Build
go build -o etl-statsmig .

# 2. Upgrade (source untouched, output to separate directory)
#    Scoring (metadata.scores) is computed and injected automatically.
./etl-statsmig upgrade \
  --in      /data/stats/archive \
  --out     /data/stats/upgraded \
  --workers 16

# 3. Validate (check every output file against its source)
./etl-statsmig validate \
  --in      /data/stats/archive \
  --out     /data/stats/upgraded \
  --ref     /data/stats/new_reference_samples \
  --workers 8 \
  --verbose 2>&1 | tee upgrade_validation.log

# 4. Check exit code
echo "Exit: $?"
```

Non-zero exit from any command means at least one file failed. Check the log for `[FAIL]` / `WARN` lines.

To verify the scoring algorithm independently against reference files:

```bash
./etl-statsmig scorecheck --ref /data/stats/new_reference_samples
```

## Error Handling

- **Upgrade errors** are logged per-file with full path and error reason. Processing continues for all other files.
- **Walk errors** (e.g. permission denied on a subdirectory) are logged and skipped; the walk continues.
- Both commands exit with code `1` if any error occurred, suitable for CI or shell `&&` chaining.
- Already-upgraded files are silently skipped during upgrade (idempotent).

## Known Limitations

1. **`obj_carrierkilled` victim/weapon fields** — only the `objective` name is emitted into gamelog events; the `victim` and `weapon` fields present in old-format `obj_carrierkilled` entries remain in `player_stats` only and are not reconstructed into gamelog events.

2. **No `unixtime` on events when `round_start_unix` absent** — very early files (before the unix timestamp was added to the Lua module) will produce gamelog events without `unixtime`. This is logged as a warning by `validate`.

8. **Alpha side detection irrecoverable for some matches** — `rescore` and `scorecheck` determine `round.alpha_side` from a parity formula `(map_num + round_num) % 2`. This formula is correct for the majority of matches but fails when:
   - A map was **restarted** mid-match: both plays appear as the same `map_num + round_num`, but teams may have reconfigured sides between attempts. The formula gives the same answer for both, so it is wrong for the restart play.
   - **ng_mode matches** (`state: "unknown match"`): the Lua module uses a lower detection threshold (65%) and scans live player slots. The actual side can differ from the formula, especially when players swapped ET teams voluntarily.
   - Any other match where teams played a different side than the convention predicts.

   In all cases the root cause is the same: alpha's ET-team assignment is determined by `detect_alpha_side_from_players()` from live player slot data at round start. This is not stored in the file. `match.alpha_team` uses Discord IDs, while `player_stats` uses game GUIDs — they cannot be cross-referenced to reconstruct side assignment. Match termination suppression for ng_mode is correctly applied regardless.

4. **Player spawn/revive/pickup events cannot be reconstructed** — the old Lua module had no callbacks for these events. Gamelog coverage from upgraded files is partial compared to files generated natively by the new module.

5. **Team disambiguation for teamkill detection** — uses the team field from `player_stats`. If a player has no entry in `player_stats` (disconnected before round end), their team is unknown and the event defaults to `kill`.

6. **Empty `player_stats` as array** — some very old files serialised an empty player list as `[]` instead of `{}`. The tool treats any JSON array value for `player_stats` as an empty map and continues normally.

7. **Numeric attacker/target in obituaries and damageStats** — the oldest files used integer client slot numbers (0–63) instead of GUID strings for `attacker` and `target` fields. These are preserved as-is (stringified) in gamelog events. Team-based kill/teamkill disambiguation will not work for these entries since slot numbers cannot be matched to `player_stats` entries.
